# PortWatch V4 PRD

## 1. 版本定位

PortWatch 当前已经覆盖端口扫描、进程详情、确认后释放端口、JSON、watch、TUI、服务识别、端口范围和 Windows UDP。下一阶段不再扩展到数据库、后台服务或网络分析，而是把现有能力做成更可靠的日常开发工具。

V4 的核心目标是：

> **更快定位，更容易脚本化，更难误操作。**

建议版本号：`v0.3.0`。V4 完成后，已有 `portwatch 8080`、`free`、`kill`、`find`、`watch` 和 `tui` 的基本行为必须保持兼容。

## 2. 目标用户与场景

- 启动开发服务前，快速确认端口是否可用
- 在多个监听端口中筛选某个应用、PID 或协议
- 在 PowerShell、CI 和编辑器脚本中根据结果决定下一步
- 需要终止进程时，能够看到足够上下文并获得明确的安全提示
- 在 Windows、Linux、macOS 上获得一致的命令和错误语义

## 3. 成功标准

用户可以完成以下流程：

```text
portwatch --process node --protocol tcp
    -> 只看到目标进程的 TCP 端口

portwatch info 18232
    -> 查看 PID 的完整详情和全部端口

portwatch --json info 18232
    -> 得到稳定 JSON，可被脚本解析

portwatch free 8080
    -> 确认、终止、验证，并得到明确退出码
```

V4 验收必须同时覆盖：正常结果、空结果、权限不足、进程已退出、参数错误、用户取消和 Ctrl+C。

## 4. V4 范围

### 4.1 统一查询过滤

在列表、端口范围、端口集合和 watch 命令上增加可组合过滤：

```powershell
portwatch --process node
portwatch --pid 18232
portwatch --state LISTENING
portwatch --protocol tcp --process java 3000-9000
portwatch --json --process node
portwatch --process node watch
```

要求：

- `--process` 对进程名做不区分大小写的子串匹配
- `--pid` 使用逗号分隔的正整数列表，例如 `--pid 18232,19500`，重复值自动去重
- `--state` 只接受当前平台支持的状态；未知状态返回参数错误
- 过滤顺序固定为：扫描 → 端口选择器 → 过滤 → 进程信息补全 → 渲染
- 表格和 JSON 使用完全相同的过滤结果和排序规则
- 无结果是成功状态，表格输出表头，JSON 输出空数组
- `--process`、`--pid`、`--state` 不能改变 `free`/`kill` 的确认逻辑

### 4.2 PID 进程详情命令

增加只读命令：

```powershell
portwatch info 18232
portwatch --json info 18232
```

详情至少包含：

- PID、进程名
- 可执行文件路径
- 命令行
- 工作目录（可获取时）
- 用户（可获取时）
- 当前由该 PID 占用的端口列表

要求：

- 这是只读命令，不允许触发 Kill
- 进程不存在时返回明确错误和非零退出码
- 某个字段无权限读取时显示 `-`，不隐藏其他可用字段
- JSON 使用新的 `process` 响应对象；已有端口响应继续使用 schema `2`
- 同一个 PID 的端口按协议、端口、地址稳定排序

### 4.3 可脚本化退出码

定义并记录稳定退出码：

| 退出码 | 含义 |
| --- | --- |
| `0` | 查询成功、空结果、用户取消或 watch 收到 Ctrl+C |
| `2` | 参数、端口、PID 或过滤条件无效 |
| `3` | 扫描或进程信息读取失败 |
| `4` | 权限不足 |
| `5` | Kill 失败或 Kill 后验证失败 |

要求：

- 表格、JSON、watch 和 TUI 的错误退出行为有测试覆盖
- JSON 错误只写 stderr；stdout 不得混入提示、表头或日志
- 退出码文档写入 README 和 `prd/v4.md`
- 不直接调用 `os.Exit`，继续由 `cmd/portwatch` 统一退出

### 4.4 安全策略和可审计输出

- `free`、`kill` 默认继续要求明确确认
- 增加 `--yes` 前必须单独评审；V4 默认不提供无确认 Kill
- PID 4、系统关键进程和当前 PortWatch 自身应给出额外警告并拒绝默认终止
- Kill 前输出 PID、进程名、命令行、可执行路径和关联端口
- Kill 后验证进程是否退出；`free` 还必须验证目标端口是否释放
- 记录一次操作摘要到 stdout（成功）或 stderr（失败），不写本地日志文件
- 权限错误要给出管理员或 sudo 提示，但不能泄漏不必要的命令行敏感信息

### 4.5 跨平台和发布质量

- Windows：TCP、UDP、进程详情和 Kill 行为保持当前能力
- Linux：TCP 查询、进程详情和错误语义通过实机或容器验收
- macOS：TCP 查询、进程详情和错误语义通过实机验收
- 不支持的平台返回明确的 `not supported`，不能编译失败或 panic
- CI 至少执行 `go test ./...`、`go vet ./...`、`go build ./...` 和 Windows/Linux/macOS 交叉编译
- 发布包包含版本号、SHA256 校验和以及最小安装说明

## 5. JSON 合同

V4 不修改现有端口响应的 `schema_version: "2"`。新增 `info` 响应使用独立的响应类型，示例：

```json
{
  "schema_version": "1",
  "process": {
    "pid": 18232,
    "name": "java.exe",
    "executable": "C:\\Program Files\\Java\\bin\\java.exe",
    "command": "java -jar order-service.jar",
    "working_dir": "D:\\Projects\\order-service",
    "user": "developer",
    "ports": [8080, 8081]
  }
}
```

字段规则：

- 数组永远输出 `[]`，不输出 `null`
- 可选字符串读取失败时输出空字符串或 `-`（表格层负责显示）
- JSON 字段使用 snake_case
- 新增字段必须补充样例和兼容性测试

## 6. 非目标

V4 明确不做：

- 无确认自动 Kill、批量 Kill 或 Kill 全部同名进程
- 网络流量抓包、防火墙规则、连接质量分析
- Docker、Kubernetes、服务注册中心或自动启动开发服务
- 数据库、常驻后台进程、Web UI、MCP、AI
- 复杂配置中心、插件系统或新的 CLI 框架
- 把 TUI 设为默认无参数入口

## 7. 技术约束

- 保持现有 Go 包结构和标准库优先原则
- 不新增 Repository、Service、DAO 等中间层
- 平台实现继续使用 build tags 隔离
- 查询过滤放在 `internal/command` 的编排层，扫描器只负责返回原始端口记录
- `info` 复用现有 `process.Manager` 和 `port.Scanner` 接口，不复制 Windows API 逻辑
- JSON 模型继续放在 `pkg/model`
- 所有新增行为通过接口注入测试替身；禁止依赖真实机器端口才能通过单元测试

## 9. 验收清单

### CLI

- [ ] 单端口、范围、端口集合和全量列表都支持过滤
- [ ] `info <pid>` 能显示详情和端口反查
- [ ] 无效过滤条件返回退出码 `2`
- [ ] 查询空结果返回退出码 `0`

### JSON

- [ ] 现有 schema `2` 端口响应无回归
- [ ] `info` JSON 可被标准解析器读取
- [ ] stdout/stderr 分离测试通过
- [ ] 空数组、权限缺失字段和进程消失均有测试

### 安全

- [ ] 未确认不会终止进程
- [ ] 关键 PID 有保护
- [ ] Kill 和 free 均有终止/释放验证
- [ ] 退出码与错误文案一致

### 质量

- [ ] `go test ./...`
- [ ] `go vet ./...`
- [ ] `go build ./...`
- [ ] Windows 实机查询、UDP、free、info、TUI 手测
- [ ] Linux/macOS 实机或 CI 验收 TCP 和错误语义
- [ ] README、`--help`、发布包说明一致

## 10. 发布建议

V4 完成后发布 `v0.3.0`。先发布过滤和 `info` 这两个高频只读能力；稳定退出码和跨平台 CI 是同一版本的质量门槛。批量操作、无确认模式和更复杂的服务识别继续留在 V5 评估，不作为 V4 的隐含承诺。

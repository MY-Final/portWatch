# PortWatch V2 PRD

## 1. 版本定位

PortWatch V1 已经完成端口查询、进程信息读取、安全 Kill、端口释放验证，以及基础的 `find`、`watch` 和 JSON 能力。

V2 的目标不是扩大系统边界，而是把这些能力整理成一个真正适合日常开发工作的工具：

> **查询结果可信，脚本输出稳定，交互操作可恢复。**

V2 优先完善现有 CLI 和已经存在的 TUI 包，不新增数据库、后台服务、Web UI、AI 或 MCP。

## 2. 目标用户

- Windows 上运行 Node、Java、Python、Go 等开发服务的开发者
- 需要在 PowerShell、CI 或脚本中检查端口的开发者
- 不熟悉 `netstat`、`tasklist`、`taskkill` 参数组合的开发者

## 3. V2 成功标准

用户可以完成以下流程，而不需要记忆系统命令：

```text
portwatch 8080
    -> 看见端口、PID、进程名和命令行

portwatch --json 8080
    -> 得到稳定、可解析的 JSON

portwatch watch
    -> 看到端口新增和释放，并能识别对应进程

portwatch tui
    -> 刷新、搜索、查看详情，并在确认后终止进程
```

V2 不改变已有 `portwatch 8080`、`portwatch free 8080`、`portwatch kill <pid>` 的基本行为。

## 4. V2 范围

### 4.1 TUI 入口与交互完善

新增显式命令：

```powershell
portwatch tui
```

要求：

- 保留无参数时的表格输出，避免破坏脚本和已有用户习惯
- `r` 重新扫描端口
- 上下键选择端口，`Enter` 查看详情
- `/` 进入搜索输入，`Esc` 清除搜索
- `k` 显示 Kill 确认，`y` 执行，`n` 或 `Esc` 取消
- Kill 成功或失败后重新加载数据并显示结果
- 终端窗口较窄时不能产生不可读的重叠内容
- Ctrl+C 和 `q` 正常退出

详情至少包括：端口、协议、状态、PID、进程名、命令行、可执行路径；无法读取的字段显示 `-`，不能导致整个列表消失。

### 4.2 Watch 可用性

保留命令：

```powershell
portwatch watch
portwatch --interval 2s watch
portwatch watch 8080
```

要求：

- 默认间隔为 1 秒，间隔必须大于 0
- 可选端口参数只监控一个端口，例如 `portwatch watch 8080`
- 新增事件使用 `+`，移除事件使用 `-`
- 事件中显示端口、协议、PID 和进程名
- 同一端口由多个 PID 监听时，每条记录独立比较
- 进程信息读取失败时仍输出端口事件，并在名称处显示 `-`
- 收到 Ctrl+C 后停止轮询并以成功状态退出
- 扫描失败时输出错误并继续轮询；连续失败不能导致忙循环

V2 不要求实现复杂的终端重绘；清晰、稳定的事件流优先于视觉效果。

### 4.3 JSON 合同

以下命令必须支持 JSON：

```powershell
portwatch --json
portwatch --json 8080
portwatch --json free 8080
portwatch --json find node
```

通用响应包含：

```json
{
  "schema_version": "1",
  "ports": []
}
```

端口对象字段：

```json
{
  "port": 8080,
  "protocol": "TCP",
  "local_addr": "127.0.0.1",
  "remote_addr": "0.0.0.0",
  "state": "LISTENING",
  "pid": 1234,
  "process_name": "node.exe",
  "executable": "C:\\Program Files\\nodejs\\node.exe",
  "command": "node server.js"
}
```

要求：

- 成功输出只写 stdout
- 错误输出只写 stderr，不能污染 JSON
- 空结果使用空数组，而不是 `null`
- 字段名称和 `schema_version` 保持稳定
- `free --json` 返回 `status`、`port` 和可选的 `error`
- JSON 输出排序规则与表格输出一致

V2 不承诺 JSON 向后兼容多个大版本；字段变更必须提升 schema 版本并同步文档。

### 4.4 服务识别接入

将现有服务识别器接入表格和 JSON 输出，但识别结果必须是辅助信息：

- 识别依据：进程名、命令行、工作目录和端口
- 无法确认时显示 `Unknown`
- 不修改原始进程名和命令行
- 不因为识别器失败而影响端口查询

建议显示列：`SERVICE`。JSON 增加可选的 `service` 对象：

```json
{
  "name": "Vite",
  "type": "frontend",
  "confidence": 90
}
```

## 5. 安全与错误处理

- `free` 和 `kill` 默认必须明确确认，空输入等同于取消
- 不允许通过普通命令误杀 PID 4 等关键系统进程
- Kill 后必须验证进程退出；`free` 还必须验证端口已释放
- 权限不足时提示以管理员身份运行，并保留可判断的错误类型
- 目标进程已经退出时，显示“进程不存在或已退出”，不输出堆栈
- 所有库函数返回 error，不调用 `panic`、`os.Exit` 或直接终止宿主进程

## 6. 非目标

V2 明确不做：

- UDP 扫描和 TCP/UDP 混合查询
- 端口范围和端口集合语法
- Docker、服务注册中心或开发环境自动启动
- 常驻后台进程、数据库、Web UI、MCP、AI
- 自动 Kill（无确认模式）
- 改变默认命令输出为 TUI

UDP、端口范围和更完整的跨平台能力进入 V3 候选。

## 7. 技术约束

- 保持现有 Go 包结构和依赖；不引入 CLI 框架或新的服务层
- 平台差异继续使用 build tags 隔离
- `internal/command` 负责编排和输出，`internal/port`、`internal/process` 负责平台能力
- TUI 只依赖既有 Bubble Tea 包
- JSON 模型继续放在 `pkg/model`
- 生产逻辑必须可通过接口注入测试替身

| V2-02 | 完善 TUI 搜索、选择和详情状态 | `internal/tui/*.go` | V2-01 |

| V2-05 | 统一 JSON 的 find/free/list 响应 | `internal/command/json.go`, `pkg/model/json.go` | 无 |
